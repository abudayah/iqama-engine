# Security Policy

## Supported versions

Only the `main` branch is supported. The `prod` branch is generated by CI from `main` (built output only); report issues against `main`.

## Reporting a vulnerability

Please report security problems privately through GitHub: open the repository's **Security** tab and choose **Report a vulnerability** (GitHub private vulnerability reporting / Security Advisories). Do not open a public issue or pull request for a vulnerability.

Include what you found, how to reproduce it, and the impact you expect. We will acknowledge the report and keep you updated in the advisory thread.

## Scope

In scope:

- The API in `src/` (all routes under `/api/v1/`), including authentication, authorization and input validation
- Anything that lets someone change the published prayer times without the admin key
- Leaking of secrets or database contents
- The deployment scripts and workflow in this repository (`deploy.sh`, `.cpanel.yml`, `.github/workflows/`)
- Vulnerable dependencies that are actually reachable by this application

Out of scope:

- Findings that need physical access to the server or a compromised admin key
- Denial of service by sending a very large volume of requests (there is no rate limiting, see below)
- Issues in third-party services (GitHub, hosting provider) or in the separate UI repository

## Authentication model (as implemented)

There are no user accounts, roles or sessions.

- Administration uses **one shared admin key**. The caller sends it in the `x-api-key` header and the server compares it with the `ADMIN_PASSWORD` environment variable. The comparison hashes both values with SHA-256 and uses `timingSafeEqual` (`src/auth/api-key.guard.ts`).
- If `ADMIN_PASSWORD` is not set on the server, every protected request is rejected with `401`.
- Protected routes: everything under `/api/v1/admin/` (overrides, cache clear, Azan configuration), and in `/api/v1/hijri-calendar` the moon-sighting `POST`/`DELETE` `override` and `POST` `qiyam-config`.
- Public routes (no key): `GET /api/v1/schedule`, `GET /api/v1/health`, and `GET` `status`, `eid-prayers` and `qiyam-config` under `/api/v1/hijri-calendar`.
- Because the key is shared, actions are not attributable to a person, and the key cannot be revoked per person. Rotating it means changing `ADMIN_PASSWORD` and restarting the service.
- The key is sent in a request header, so the service must be served over HTTPS. The application itself does not terminate TLS.

## Secrets handling

- `.env` is listed in `.gitignore` and must never be committed. `.env.example` is the only tracked file and holds placeholders only.
- `ADMIN_PASSWORD` and `DATABASE_URL` are secrets. In CI they are GitHub Actions secrets (see `.github/workflows/build-and-deploy.yml`); other settings are GitHub Actions variables.
- Do not commit database files (for example `prisma/*.sqlite`) or paste real keys into issues, pull requests or logs.
- If a secret is committed by mistake, treat it as leaked: rotate it first, then remove it from the repository.

## CORS

CORS is controlled by the `CORS_ORIGIN` environment variable (`src/main.ts`):

- Not set or empty: CORS headers are not sent.
- A comma-separated list: only those origins are allowed.
- `*`: any origin is allowed. This is intended for local development only.
- Allowed methods are GET, POST, PUT, PATCH, DELETE and OPTIONS; allowed request headers are `Content-Type`, `x-api-key` and `Cache-Control`; credentials are not allowed.

CORS only limits browsers. It is not a substitute for the admin key.

## Other protections, and what is not present

- Present: a global `ValidationPipe` (`whitelist: true`) validates request bodies and query parameters with DTOs; all responses are sent with `Cache-Control: no-store`; the Prisma client is used for database access.
- Not present: HTTP security headers middleware (`helmet` is not a dependency), and rate limiting or throttling (no such package or code in the repository). Brute-force attempts on the admin key are not slowed down by the application; add limits at the reverse proxy or hosting layer if the service is exposed publicly.
- The public `GET /api/v1/health` endpoint returns the database error message when the database check fails.

## Dependencies

- Dependencies are pinned through `package-lock.json` and installed with `npm ci` in CI.
- No automated dependency update tool (such as Dependabot) is configured in this repository. Dependencies are updated manually; running `npm audit` periodically is recommended.
- Pull requests that add a dependency should say why it is needed and that it is actively maintained.
